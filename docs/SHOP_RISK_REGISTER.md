## 3. Deep-Dive Risk Analysis & Engineering Defenses

### 3.1 Technical & Data Concurrency Risks

#### Concurrency & Overselling (`TECH-R01`)
* **Scenario:** Two customers attempt to submit an order for the final remaining GeForce RTX 4070 Super at the exact same millisecond.
* **Failure Mode:** If the application checks stock via `product = await ShopProduct.findById()` and then saves via `product.save()`, both requests see `stockQuantity = 1`, and both succeed, driving stock to negative and causing an embarrassing customer cancellation.
* **Defense:** Enforce MongoDB atomic conditional update:
  ```javascript
  const product = await ShopProduct.findOneAndUpdate(
    { _id: productId, stockQuantity: { $gte: quantity } },
    { $inc: { stockQuantity: -quantity } },
    { new: true }
  );
  if (!product) {
    throw new ConflictException("Insufficient stock to fulfill request.");
  }
  ```

#### Transaction Environment Divergence (`TECH-R02`)
* **Scenario:** While the production Atlas cluster (`atlas-8q6zvi-shard-0`) is a 3-node replica set that natively supports transactions, developer laptops or lightweight CI test runners often run a single standalone mongod instance.
* **Failure Mode:** Code requiring `session.startTransaction()` crashes in development or test suites with:
  `MongoServerError: Transaction numbers are only allowed on a replica set member or mongos`.
* **Defense:**
  1. Do not use transactions for single-product stock reservation; native atomic updates are non-transactional and 100% portable.
  2. For multi-item orders, check `mongoose.connection.client.topology?.description?.setName` before initiating a session, or ensure all Docker compose test setups run with `--replSet rs0`.

---

### 3.2 Business & Supplier Fulfillment Risks

#### Supplier Price & Stock Volatility (`PRIC-R01` / `BUS-R01`)
* **Scenario:** A customer places an order for an AMD Ryzen 7 7800X3D on Friday night under `supplier_order` fulfillment mode. On Monday morning, the distributor increases wholesale price by 10% or announces a national stockout.
* **Defense:**
  1. Product detail pages explicitly state: *"Fulfillment by distributor partner. Price and availability confirmed via phone prior to payment."*
  2. The initial order submission does not accept payment; the customer incurs zero financial friction, so if an order must be adjusted or cancelled, no refund fees or bank disputes arise.
  3. The admin dashboard flags supplier lead time (`supplierLeadTimeDays`) and lists distributor contact details directly in the order confirmation drawer.

---

### 3.3 Security, Authorization & Privacy Risks

#### Customer PII Exposure (`PRIV-R01`)
* **Scenario:** Order submission endpoints require customer phone numbers, delivery addresses, and personal names.
* **Defense:**
  1. `GET /shop/orders/:id` endpoint validates that `req.userInfo._id === order.user` OR `req.userInfo.role === 1`.
  2. Guest orders receive a cryptographically random, URL-safe lookup token (e.g. `orderLookupToken = crypto.randomBytes(24).toString('hex')`) that must be provided in the query string to view the guest order status.
  3. Order logs and error traces strip the customer phone number and detailed delivery street address before writing to system log files.
